手动验证清单经独立只读核查并修正（verify_mode_006 的交付物质量控制）

总控为 TASK-006 编写了实机验证清单 .workflow-kit/docs/TASK-006-MANUAL-VERIFICATION.md（用户决断 verify_mode_006 = 门禁 + 总控列步骤、用户实机确认）。在交付给用户之前，总控派发了一个独立只读子代理（4447d2b1，未参与编写）逐条核对清单中的 13 条行号与技术断言。

核查结论：13 条中 12 条 TRUE、0 条 FALSE、1 条「字面成立但需限定」。行号引用几乎全部精确。但发现 4 处必须修正的问题，总控已全部修正：

1. **不安全步骤（最重要）**：原「方式 B」指导用户直接编辑 src-tauri/tauri.conf.json 把 bun 改成 npm，并靠「验证完请改回、不要提交」。但 src-tauri/ 在 TASK-006 的 protected_paths 内，且依赖用户记得还原一个受跟踪文件。核查者指出 Tauri CLI 本身支持非破坏性合并覆盖。总控已独立实测确认该参数存在（node_modules/.bin/tauri.cmd dev --help 显示 `-c, --config <CONFIG>  JSON strings or paths to JSON, JSON5 or TOML files to merge with the default configuration file`），并改为在仓库外建覆盖文件 + `npm run tauri dev -- -c <file>`，无需改回、不会误提交受保护文件。

2. **协议相关假失败（工艺缺陷）**：原场景 2 让用户「设为 4 → 期望 4 个任务」，但 getImageBatchCount（imageGenerationExecution.ts:468-475）开头即 `if (config.hasOpenAIImageControls) return 1;`，且检查器该控件被 `config.hasGeminiImageControls` 包住（ImageGeneratorInspector.tsx:348-357）。总控已独立读取这两处代码确认。后果：在 OpenAI 协议节点上做该场景只会看到 1 个任务，属正常行为，用户会误判为不通过。已在场景 2 前置显著警示并说明如何确认协议（控件能显示即为 Gemini 协议）。

3. **前置条件错位（框架问题）**：清单描述的是修复后的期望行为，但当时 src/ 尚未修改、门禁仍为 6 FAIL。核查者据此判定「不要在此刻交给用户」，否则场景 1-4 必然复现反例。总控已在清单顶部加「使用前提」区块，明确只在修复落地后适用，并要求以交付时的门禁实际输出为准。

4. **退出码表述与事实相反**：原文写默认模式「期望 6 PASS / exit 0」、--expect-red「期望 exit 1」，但那是修复后的目标态；修复前默认模式是 exit 1、--expect-red 是 exit 0。已改为「修复前 / 修复后」三态对照表。总控并已存档修复前红状态原始输出 .workflow-kit/tasks/evidence/BASELINE-gate-red-TASK-006.txt（5870 B、0 乱码、0/6 PASS、exit 1），以满足「红→绿」硬性验收要求。

另修正的次要项：暂停按钮引用由 QueuePanel.tsx:110-115 改为 :111-118（onClick 在 :114）；路径 components/queue 更正为 components/panels（核查者指出）；场景 4 补充重试按钮仅对 error/cancelled 渲染（QueuePanel.tsx:217）、重试会新增任务而失败记录仍在列表，故判据是「新增活动任务数」；方式 B 补充说明 src-tauri/target/debug/nextcreator.exe 是 9/27 旧构建、可启动但不含修复，不能用于验证 REQ-001。
