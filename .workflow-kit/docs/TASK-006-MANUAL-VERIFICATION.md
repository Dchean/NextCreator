## 0. 启动前必读：本机启动方式

`src-tauri/tauri.conf.json` 里 `beforeDevCommand` 是 `bun run dev`，
但**本机没有安装 `bun`**（已实测 `Get-Command bun` 为空），README 第 74-80 行写的
`bun install` / `bun run tauri dev` **在本机不可直接照抄**。

可用替代（二选一）：

- **方式 A（纯前端预览）**：`npm run dev` → 浏览器打开 `http://localhost:1420`。
  注意：这种方式没有 Tauri 后端，图片生成、`app-data.json` 持久化等 IPC 会失败或走降级路径。
  **适合验证 REQ-002（连点/批量/暂停，属纯前端状态逻辑）**，
  **不适合验证 REQ-001（重启恢复，依赖真实持久化）**。
- **方式 B（完整桌面应用，REQ-001 必须用它）—— 用配置覆盖，不要改受保护文件**：

  `src-tauri/` 在 TASK-006 的 `protected_paths` 内，**不要直接编辑 `tauri.conf.json`**。
  Tauri CLI 支持非破坏性合并覆盖（已用 `tauri dev --help` 实测确认该参数存在）：

  ```powershell
  # 1) 在仓库外（或临时目录）建一份只含覆盖项的文件，例如 %TEMP%\nc-dev-override.json：
  #    { "build": { "beforeDevCommand": "npm run dev", "beforeBuildCommand": "npm run build" } }
  # 2) 启动时合并进去，原 tauri.conf.json 保持不动：
  npm run tauri dev -- -c "$env:TEMP\nc-dev-override.json"
  ```

  这样**不需要改回**，也不会误提交受保护文件。

  **若 `cargo` 因 TLS 问题无法联网拉依赖**：注意 `src-tauri/target/debug/nextcreator.exe`
  是 **9/27 的旧构建产物**，它能启动，但**不包含本次修复**，因此不能用来验证 REQ-001。
  若无法重新构建，就如实告诉我「未能实机验证 REQ-001」，不要凭门禁通过就认可它。
  （`cargo` 失败这一结论**继承自** ADR-0002 / REFACTOR-REVIEW 的既有证据，本次未重新实测。）

## 场景 1：连点（REQ-002 核心）

1. 画布上放一个 **图片生成** 节点，连好提示词输入，确保「生成数量」= **1**。
2. 在生成按钮上**快速连点 3 次**（不要等上一次结束，越快越好）。
3. 打开右侧「生成队列」面板。
4. **期望**：队列里该节点**只有 1 个任务**；不会出现 2 个或 3 个同节点任务。
5. **反例（修复前）**：会出现 2-3 个同节点任务并发写同一节点，节点状态互相打架。

## 场景 2：批量（REQ-002 不得误伤批量）

> **⚠ 前置条件：必须用 Gemini 协议的节点。**
> 批量拆分**只对 Gemini 协议生效**。`getImageBatchCount`
> （`src/services/imageGenerationExecution.ts:468-475`）开头就有
> `if (config.hasOpenAIImageControls) return 1;` —— **OpenAI 协议节点恒返回 1，永不拆分**，
> 且检查器里那个「生成数量（并发任务）」控件（`ImageGeneratorInspector.tsx:348-357`）
> 被 `config.hasGeminiImageControls` 包住，**在 OpenAI 协议节点上根本不渲染**。
> 若你拿 OpenAI 协议节点做本场景，会只看到 1 个任务，**那是正常行为，不是缺陷** —— 别误判为不通过。

1. 选中一个 **Gemini 协议**的图片生成节点，右侧检查器找「**生成数量（并发任务）**」（`ImageGeneratorInspector.tsx:350`）。
   若要确认协议：该控件**能显示**即说明是 Gemini 协议。
2. 设为 **4**（该控件写入字段 `n`，`:357` `updateData({ n: Number(opt.value) })`）。
3. 点一次生成。
4. **期望**：队列中出现 **4 个**该节点任务（每项显示 `1/4`、`2/4` … 的批量标记），
   且这 4 个是**一次点击合法产生的**。
5. 等这 4 个跑完（或全部取消），**再点一次生成**。
6. **期望**：仍然产生**完整 4 个**新任务 —— 不能因为「历史上已有该节点任务」而被锁死。
7. **这是最容易改错的一条**：若逐个任务判重，批量会被截断成 1 个，那就是不通过。

## 场景 3：暂停态（门禁覆盖不到，必须人工确认）

1. 打开「生成队列」面板，点右上角**暂停**按钮
   （`src/components/panels/QueuePanel.tsx:111-118`，`onClick={togglePaused}` 在 `:114`）。
2. 确认队列处于暂停状态。
3. 回到图片生成节点，**在暂停状态下连点生成 3 次**。
4. **关键期望**：即使用户在暂停时连点，该节点也**只应产生 1 个任务**。
   暂停**不应该**让重复入队保护失效。
5. 然后点**恢复**，观察是否只执行 1 个任务。
6. **反例**：暂停时能累积多个任务（3 次点击 → 3 个任务，或批量时 4 次 → 12 个）。
   原因是暂停时生成按钮**仍可点**（`src/components/nodes/ImageGeneratorNode.tsx:215` 的
   `canRun` 不含 `paused`，该文件里根本没有 `paused` 这个词），而 `data.queued`
   在第一个 `await` 之后才写入（`useImageGeneratorExecution.ts:34` 是首个 `await`，
   `:86-90` 才写 `queued`）。

## 场景 4：重试（retry 绕过入口守卫）

> **注意**：重试按钮**只对 `error` / `cancelled` 状态的任务渲染**
> （`QueuePanel.tsx:217`），所以必须先制造一个失败任务。
> 且重试会**新入队一个任务**，原来那条失败记录**仍留在列表里** ——
> 判据看的是「**新增的活动任务数**」，不是「列表里那条失败记录」。

1. 让某个任务失败（可用非法参数制造错误，或断网让请求失败）。
2. 确认该任务变成 `error`（列表中出现重试按钮）。
3. 在队列面板里连续点该任务的**重试**按钮 3 次（`QueuePanel.tsx:222` 的 `onClick={() => retry(job.id)}`）。
4. **期望**：该节点只产生 **1 个**新的活动任务（`queued`/`running`），不累积增长。
   失败记录本身仍在列表里，这是正常的。
5. **原理**：`retry`（`queueStore.ts:90-103`）直接调用 `enqueue`，
   **绕过** `handleGenerate`，所以只有把守卫下沉到 `store.enqueue` 才拦得住。

## 场景 5：重启恢复（REQ-001，必须用方式 B）

1. 启动应用，放一个图片生成节点，点生成。
2. 在任务**处于排队或进行中**时，**强制关闭应用**（不要等它跑完）。
3. 重新启动应用。
4. **期望**：
   - a) 该任务**不再**永久停留「排队中」；
   - b) 节点**不再被锁死**（按钮可用，不显示"排队中"）；
   - c) 遗留任务**自动恢复并继续生成**（这是已确认的产品行为：会产生真实 API 费用）；
   - d) 若该节点已不存在（比如换了画布），任务应落到**错误/可重试**状态，
        **不得**卡在 `queued` 或 `running`。
5. **反例（修复前）**：节点永久显示「排队中」，按钮一直禁用，重启也永不执行。
6. 额外注意：**不得出现崩溃循环**（若恢复后立即失败，不能无限重启重试）。
